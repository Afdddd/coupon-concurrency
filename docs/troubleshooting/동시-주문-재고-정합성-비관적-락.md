# 동시 주문 시 재고 정합성 깨짐과 비관적 락

## 문제

주문 기능의 동시성 문제를 검증하기 위해 재고 100개 상품에 대해 100개의 동시 주문 요청을 발생 

정상이라면 최종 재고는 0이 되어야 하지만, 테스트 결과 재고가 90개 남아 있었다. 또한 로그에는 데드락이 발생한 기록도 확인

## 재현

동시 요청을 정확히 재현하기 위해 `ExecutorService`와 `CountDownLatch`를 사용했다.

- `ExecutorService`로 스레드 100개를 띄운다.
- `CountDownLatch`로 스레드를 모아뒀다가 한 번에 풀어 동시에 실행시킨다.(내부에 큐가 존재해 스레드를 큐에 넣어두고 설정한 countdown 0이 되면 큐에 잠재워져있는 스레드를 깨운다.)
- DB는 Testcontainers로 운영과 같은 MySQL을 띄운다.
  H2는 락 동작과 방언이 달라 데드락이 재현되지 않는다.

```kotlin
val threadCount = 100
val executor = Executors.newFixedThreadPool(threadCount)
val readLatch = CountDownLatch(1)            // 출발 신호
val doneLatch = CountDownLatch(threadCount)  // 완료 대기

repeat(threadCount) {
    executor.submit {
        try {
            readLatch.await()                // 출발선에서 대기
            orderService.createOrder(
                userId,
                OrderCreateRequest(listOf(OrderItemRequest(productId, 1)))
            )
        } catch (e: Exception) {
            e.printStackTrace()
        } finally {
            doneLatch.countDown()
        }
    }
}
readLatch.countDown()   // 전원 동시 출발
doneLatch.await()       // 100개가 끝날 때까지 대기

val product = productRepository.findById(productId).get()
assertEquals(0, product.stock)   // 락이 없으면 90이 나와 실패한다
```

## 분석

### 재고가 덜 줄어든 이유 — lost update
동시에 여러 트랜잭션이 동일한 재고를 조회한 뒤 각각 차감 값을 계산하면서 Lost Update가 발생했다.

예를 들어 두 트랜잭션이 모두 재고 99를 조회한 경우:

- 트랜잭션 A → 98 계산
- 트랜잭션 B → 98 계산
- 두 트랜잭션 모두 `stock = 98`로 UPDATE

결과적으로 재고는 두 번 차감되어야 하지만 한 번만 차감된다.

원인은 JPA Dirty Checking이 `stock = stock - 1` 형태가 아닌, 애플리케이션에서 계산된 값을 기준으로 UPDATE를 수행하기 때문이다.

### 데드락

Hibernate SQL 로그를 분석한 결과 주문 처리 과정은 다음 순서로 수행됐다.

1. user select
2. order insert - x락
3. product select 
4. orderProduct insert — x락 + 부모인 order, product에 S락
5. order update
6. product update — 재고 차감 더티 체킹, X락 필요

문제는 공유 자원인 product다. 4번에서 S락을 잡고, 6번에서 X락을 잡으려다 충돌한다.

- **스레드 1 & 스레드 2**가 동시에 `Product`를 일반 `SELECT`로 읽음. (락 없음)
- **스레드 1**: `OrderProduct`를 `INSERT`하면서 부모인 **`Product`에 S락**을 획득
- **스레드 2**: `OrderProduct`를 `INSERT`하면서 부모인 **`Product`에 S락**을 획득 (S락끼리는 서로 호환)
- **스레드 1**: 더티 체킹으로 `Product` 재고를 줄이려고 **X락(Write)을 요청**. 하지만 이미 `스레드 2`가 S락을 쥐고 버티고 있어서 **대기** 상태. (트랜잭션이 안 끝났으니 락을 못 품)
- **스레드 2**: 마찬가지로 `Product` 재고를 줄이려고 **X락을 요청**. 이번엔 `스레드 1`이 S락을 쥐고 있어서 **대기** 상태

그 결과 서로의 락이 풀리길 기다리다 InnoDB가 데드락을 감지해 한쪽을 롤백한다.

## 해결

재고를 조회할 때 `SELECT ... FOR UPDATE`로 바로 X락을 잡는다.

```kotlin
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select p from Product p where p.id = :id")
fun findByIdForUpdate(id: Long): Product?
```

```kotlin
// OrderService.createOrder
val product = productRepository.findByIdForUpdate(item.productId)
    ?: throw EntityNotFoundException("Product not found")
product.reduceStock(item.quantity)
```

3번 시점에 X락을 잡으니 다른 스레드는 그 앞에서 한 줄로 대기한다.

- 재고 조회 시점에 X Lock 선점
- 동일 상품에 대한 동시 접근 차단
- Lost Update 방지
- S Lock → X Lock 승급 과정 제거
- Deadlock 해소

비관적 락은 트랜잭션 범위 내에서 유지되므로 조회부터 재고 차감까지 하나의 트랜잭션으로 관리해야 한다.

## 결과

동일한 테스트를 다시 수행한 결과:

- 재고 100 → 0 정상 차감
- Lost Update 미발생
- Deadlock 로그 미발생

동시 주문 상황에서도 재고 정합성을 보장할 수 있게 되었다.

## 고려 사항

비관적 락은 정합성을 보장하는 대신 처리량이 감소할 수 있다.

현재는 재고 정합성이 우선인 주문 시스템 특성상 비관적 락을 적용했지만, 향후 트래픽 증가 시 낙관적 락이나 별도의 재고 처리 전략을 검토할 수 있다.
