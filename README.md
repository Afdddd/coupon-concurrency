# 선착순 쿠폰 발급 시스템 — 동시성 제어

대량 동시 요청 환경에서 발생하는 동시성 문제를 **실행 순서(Transaction Schedule)** 관점으로 분석하고,
DB 레벨 동시성 제어 기법을 단계별로 적용·측정한 기록.

> 정리 글: [선착순 1,000장 쿠폰이 1,967장 발급된 이유](https://inyeop.notion.site/1-000-1-967-3550c52c121980d7937dfcd3f5e8b5c4)

## 기술 스택

- Kotlin + Spring Boot + JPA
- MySQL 8.0 (InnoDB, 기본 격리수준 REPEATABLE READ)
- k6 (부하 테스트)

## 핵심 API

```
POST /coupon/{couponId}/issue?userId={userId}
```

쿠폰 조회 → 잔량 검사 → 중복 발급 검사 → 차감 → 발급 이력 저장

## 테스트 시나리오

쿠폰 1,000개 / 동시 유저 10,000명 / 1인 1요청 (k6 `per-vu-iterations`)
→ 동시성 제어가 완벽하면 발급 1,000건, 잔량 0, 성공률 10%가 기대값.

## 문제 — 1,000장 쿠폰이 1,967장 발급됨

| 항목 | 기대 | 실측 |
|---|---|---|
| 발급 이력 | 1,000 | **1,967** |
| 쿠폰 잔량 | 0 | 140 |
| 성공률 | 10% | 19.67% |

- **Lost Update**: 여러 트랜잭션이 같은 `count`를 읽고(Read) 각자 메모리에서 차감 후 덮어씀(Write). JPA dirty checking으로 UPDATE가 커밋 시점에 발생해 race 구간이 더 넓어짐.
- **데드락**: 락을 건 적 없는데도 발생. INSERT 시 FK 무결성을 위해 부모(`coupon`) row에 자동으로 걸린 **S락**을, 차감 UPDATE가 **X락으로 승급**하려다 서로 막혀 순환 대기 (`SHOW ENGINE INNODB STATUS`로 확인).
  - → 작업 순서를 `UPDATE → INSERT`로 바꿔 처음부터 X락을 선점하면 승급 데드락 회피.

## 해법별 비교

| 해법 | 잔량 | 발급 | 데드락 | TPS | 소요 |
|---|---|---|---|---|---|
| 락 없음 (baseline) | 140 | 1,967 ✗ | 발생 | 654 | 15s |
| ① SQL 원자화 (`UPDATE ... WHERE count > 0`) | 0 | 1,000 ✓ | 없음 | 1,060 | 9.4s |
| ② SERIALIZABLE | 416 | 584 △ | 폭발 | 629 | 15s |
| ③ **비관적 락** (`SELECT FOR UPDATE`) | 0 | 1,000 ✓ | 없음 | **1,214** | **8.23s** |
| ④ 낙관적 락 (`@Version`, 재시도 X) | 8 | 992 △ | 발생 | 846 | 11.8s |

- **① SQL 원자화** — 조회·차감을 한 쿼리로 묶어 X락을 즉시 획득. 단순하지만 검증/예외 처리가 복잡해지면 한계.
- **② SERIALIZABLE** — 모든 SELECT에 S락 자동 부여. 정합성은 잡지만 S→X 승급 데드락으로 트랜잭션 대량 롤백 (584건만 통과).
- **③ 비관적 락** — X락을 SELECT 시점으로 앞당겨 S락 승급 자체를 제거. 정합성 + 최고 TPS.
- **④ 낙관적 락** — 커밋 시 version 비교로 충돌 감지. 재시도 부재로 충돌 요청이 실패로 소실, FK 데드락도 못 막음.

## 결론

- 이 시나리오의 정답에 가장 가까운 건 **비관적 락** (정합성 + 최고 TPS).
- 단, 단일 서버 기준이며, 비관적 락은 X락으로 직렬화하므로 트래픽이 늘수록 대기 시간도 비례해 증가.
- **핵심 통찰**: 동시성 문제는 결국 두 트랜잭션의 read/write가 **어떤 실행 순서로 도는지, 그게 직렬화 가능한지(serializable)** 의 문제. 충돌이 100%에 가까운 선착순은 "충돌 비용을 wait로 미리 내는" 비관적 락이, "retry로 사후에 내는" 낙관적 락보다 유리.
